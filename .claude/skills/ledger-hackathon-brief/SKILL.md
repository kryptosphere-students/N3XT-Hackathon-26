## Critères de jury (sur 100)

- Exécution technique : 25
- Utilité et pertinence pour Ledger : 20
- Innovation : 20
- Expérience utilisateur : 15
- Nouveaux cas d'usage pour Ledger : 10
- Clarté, présentation, documentation : 10

Jury : Ian Rogers, Guillaume Mathias, Joshua Mo, Drake Breeding.

Pour chaque critère, repérer ce qui manque dans le projet et proposer une action concrète.

## Structure du pitch (10 min)

5 min de présentation, puis 5 min de questions. Deux présentateurs présents à Paris.

1. **Problème et utilisateur** (1 min) : pourquoi un humain doit approuver ou prouver quelque chose.
2. **Frontière** (1 min) : tableau agent autonome / humain approuve. C'est le point que Ledger demande explicitement.
3. **Primitive Ledger implémentée** (1.5 min) : montrer le code qui appelle le device, pas seulement le nom de l'outil.
4. **Démo** (1 min) : parcours court et fiable. Prévoir une vidéo de secours.
5. **Limites honnêtes** (30 s) : mode blind signing ou non, testnet ou mainnet, ce qui n'est pas sécurisé.

Les deux présentateurs doivent pouvoir répondre aux questions techniques : celui qui pitche répond au jury.

## Write-up DX (obligatoire)

Ledger lit cette partie en premier. Être direct. Quatre points :

1. **Où la doc t'a fait perdre du temps** (page, lien mort, exemple manquant).
2. **Quel workflow était confus** (ex. sandbox, contention USB, ordre d'initialisation).
3. **Quel contexte manquait** (ex. versions, prérequis, navigateur).
4. **Une suggestion concrète** (ex. « ajouter un exemple `signTypedData` dans la page DMK Signer »).

Pour l'équipe : noter les frictions pendant le build (date, commande, message d'erreur). C'est la matière de ce write-up.
